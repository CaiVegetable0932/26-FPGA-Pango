# 帧率瓶颈复验说明

先区分摄像头物理输入、FPGA 唯一结果发布、网口完整接收、网页 Canvas 提交、HDMI 新帧回调及浏览器质量计数。固定扫描、协商 30 FPS 或浏览器质量总数均不能替代唯一图像帧率；HDMI 源身份仍为 null/unverified。

## 测量工具自身的负载

实时 RAW 使用二进制 WebSocket。通用浏览器自动化的 Network 域会监听专用 Worker 的 WebSocket 内容，引入整帧调试流量。`check_preview_performance.py` 和 `check_display_bottlenecks.py` 现使用 `browser_probe.py` / `browser_probe.cjs`：复用现有工作台，只启用轻量 Runtime 观察，不启用 Network，不启动其他浏览器或关闭标签页。

采样读取已有一秒观察器的质量累计数及已协商的采集配置，不在每次采样中额外调用媒体查询。质量计数存在最多一个观察周期的采样边界误差；其掉帧数字与实际回调矛盾时仍明确保留，不能改成虚假的解码 FPS。

## 单独执行对照

```bash
cd /home/cai/26-FPGA-Pango/26-FPGA-Pango
source host/scripts/env.sh
python -B host/scripts/check_display_bottlenecks.py --seconds 20
python -B host/scripts/check_preview_performance.py --seconds 120 --preview-mode raw --label raw
python -B host/scripts/check_fpga_processing_framerate.py --seconds 20
python -B host/scripts/check_fpga_processing_framerate.py --seconds 20 --compare-original
```

第一条依次比较隐藏且关闭采集、只显示网口、双路显示、隐藏 HDMI 但继续解码以及重复窗口。它保存区间 CPU 占用而非 ps 的进程终生均值，并恢复原显示/采集设置。报告均留在 `host/reports/`，脚本成功不等于 30 FPS 验收通过。不要并行跑测试套件、其他采集器、帧级网络跟踪或 GPU 回读。

最后一条只临时改变 FPGA 显示模式，结束恢复；不修改标定参数、Flash、USB 或电源。若两种模式都低于 DVP 输入，则交接重点是共用处理链路，而不能仅断言鱼眼计算公式太慢。Windows 后续操作见 [板端开发交接](../../fpga/docs/Windows_1080p30帧率优化交接.md)。

## 正式软件策略与边界

- FPGA 源像素覆盖层通过 ResizeObserver 缓存尺寸，每帧不再强制读取布局；尺寸改变、源或元数据失效仍正确更新/清空。
- Worker 至多持有一张等待提交的位图和一张预取 RAW。转换在 ACK 后开始，额外等待超过 100ms 的 RAW 在 GPU 前丢弃；原始接收、完整性、归档及源帧统计不受预览丢弃影响。
- 诊断分别统计位图导出、Worker 到主线程等待、绘制提交和有不确定度的帧年龄。队列记录为最近收到的 Worker 状态，并注明样本年龄，不把主线程空队列当作整个流水线空队列。
- GPU 绘制与 JPEG 视频解码能力分别核对。NVIDIA 对 [JetPack 6 浏览器解码案例](https://forums.developer.nvidia.com/t/hardware-decoding-video-firefox-chromium-on-jetpack-6/306679) 的说明不能直接证明这台机器的具体插件已启用，仍须读取实际设备与解码能力。
- 原生 MJPEG 对照参照 [NVIDIA 方法与格式限制](https://forums.developer.nvidia.com/t/hardware-decoding-of-mjpeg/284525)，读取已安装插件后验证 nvjpegdec / nvv4l2decoder。fakesink、WebGL 成功或安装 GPU 插件都不能当作网页已实现硬件解码。

远程桌面编码占用也可能挤占接收/显示资源。中断远程视频会影响操作者，需先约定短时对照和自动恢复；本说明不会自动永久限制远程桌面、不更改 JetPack 或电源模式。正式运行的资源分配与板端吞吐分别验收。
