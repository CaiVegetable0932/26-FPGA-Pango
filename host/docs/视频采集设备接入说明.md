# 视频采集卡设备选择与预览接口

日期：2026-09-09。适用：系统识别为摄像头/照相机的视频输入设备，包括用户截图所示的 Hagibis 采集卡。设备名称以浏览器实际列出的内容为准，不按名称推断其输入一定来自 FPGA。

## 使用方法

1. 更新代码后先停止旧 Web 服务，再使用 Windows 的 start_web.cmd 或 Ubuntu 的 start_web.sh 重新启动；本次新增了两份前端资源，需要新服务加载资源清单。
2. 在本机页面打开“连接设置 → 视频采集卡输入”，点击“刷新设备”。
3. 如果名称没有显示，点击“授权显示设备”，在浏览器提示中允许摄像头访问。授权操作会短暂打开一个视频设备，读取列表后立即释放；不申请麦克风。优先使用列表中仍存在的已保存设备，否则由浏览器选择临时授权设备。
4. 在列表中选择 Hagibis（或实际使用的采集卡），点击“保存设备选择”。此步骤仅保存设备 ID 和名称，不打开采集卡，不要求已有 HDMI 信号。
5. 需要查看采集卡输出时，再点击设置区或右侧视频区的“打开预览”；关闭按钮释放设备。左侧 RAW8 的开始/停止按钮只控制网络接收，与采集卡互相独立。

当前没有信号时，可以停在第 4 步。选择保存于当前浏览器、当前站点的 localStorage；重开页面只恢复选择，不会自动打开设备。端口、浏览器或电脑变化后需重新选择；系统撤销权限、设备 ID 变化或清除浏览器数据后，也需重新授权/选择。浏览器禁止本地存储时，界面会提示仅在当前页面生效。

页面显示“接口已打开”只表示浏览器返回了视频轨道；黑屏、采集卡的“无信号”画面或驱动协商的尺寸/帧率均不能证明 HDMI 输入正常。界面的“协商 FPS”来自设备轨道设置，不是实测帧率。没有执行画面检测、信号验收或源帧配对。

关闭页面会释放该页面的采集卡流；后台 Python 的 RAW8 网络采集不会因关闭页面而停止。多个标签页各自管理采集卡，不应同时打开同一设备；占用时界面显示可恢复的错误。重新选择设备前先关闭当前设备，再保存新选择。

## 接入结构

~~~text
Windows 摄像头驱动 / Ubuntu 视频设备驱动
    → 浏览器 MediaDevices（枚举、权限、按 deviceId 打开）
    → PangoVideoInput 控制器 / MediaStream
    → 本机页面右侧 <video> 预览

FPGA RAW8 / UDP
    → Python UDPReceiver / WebSession
    → 左侧 RAW8 派生预览与原始证据归档（原有链路）
~~~

本次配置和采集接口位于上位机的浏览器端，Python 服务负责提供页面与已有 RAW8 核心。采集卡视频不会通过 HTTP 上传到 Python，也不会转发到云端；HDMI 原始字节归档、后端测评和与 S0 配对不属于本次接口接入。后续消费者可通过 getStream() 获取当前 MediaStream 接入处理链，不应把浏览器解码后的像素冒充 HDMI 原始证据。

- [video-input.js](../web/video-input.js)：独立的设备采集适配器，可注入 MediaDevices、存储和状态回调进行无硬件测试。
- [video-input-ui.js](../web/video-input-ui.js)：设备选择、状态、保存和预览按钮，与右侧视频区域共用一个控制器。
- [app.js](../web/app.js)：在连接设置中刷新设备，页面退出时释放适配器；不改 S0 接收启停逻辑。
- [web_server.py](../src/pango_video/web_server.py)：提供新增静态资源和本机媒体资源策略。

## 控制器接口

创建方式为 PangoVideoInput.createController({mediaDevices, storage, video, onState, secureContext})。MediaDevices 来自 navigator.mediaDevices，video 为页面的 HTMLVideoElement；getState() 不含图像数据或媒体对象。

| 方法 | 行为 |
| --- | --- |
| refresh() | 枚举 videoinput，过滤麦克风/音频输出，不申请采集流；设备变化也会刷新列表 |
| configure(deviceId) | 保存列表中用户选中的设备；不打开设备，也不测试信号 |
| authorize() | 请求摄像头权限以读取名称，临时流在成功、失败和取消后均释放 |
| open() | 按已保存的 deviceId exact 打开，audio=false；不固定 1080p30，使用设备默认协商格式 |
| close() | 关闭当前流、清空预览，保留配置；未完成的权限请求返回后立即丢弃并释放 |
| getStream() | 返回当前 MediaStream 或 null，供上位机浏览器内其他组件使用 |
| getState() | 返回配置、设备列表、生命周期和设备协商格式；源帧身份仍未验证 |
| destroy() | 页面退出时关闭流并移除设备变化监听，释放延迟返回的轨道 |

设备选择用 exact 约束，旧设备缺失时报告错误，不回退到内置摄像头。刷新列表不会自动选择或打开新设备。取消无法撤回浏览器已有的权限弹窗，因此新设备请求需等待旧请求结束；迟到的流不会接入页面。

状态包含 idle / configured / authorizing / opening / open / waiting / disconnected / error / unsupported。waiting 仅表示轨道暂时没有数据，不解释为确认无 HDMI 信号。无论状态如何，source_frame_id=null、pairing_status=unverified、signal_validation=not_performed。

Python /api/status.hdmi 保留 available=false，新增 available_scope=python_raw_capture、preview_backend=browser_media_devices、preview_state=not_reported，以说明服务端没有取得 HDMI 原始证据，也没有将某个浏览器的设备状态当作全局事实。原始证据报告和 S0 源帧身份不被浏览器选择改变。

## 平台与权限

两端共用同一份标准浏览器接口，运行仍不需要 OpenCV、Qt 或额外 Python 包。浏览器需要允许摄像头访问；本机工作台通常通过启动脚本打开系统默认浏览器。若内嵌窗口不提供视频设备接口，界面会提示在系统浏览器中打开终端显示的本机地址。Ubuntu 目标机器和真实采集卡均未在本次执行采集验证。

实现依据：[W3C Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/)，包括设备枚举、权限下的信息公开、exact 设备选择和媒体轨道生命周期。设备标签及 ID 由浏览器按站点权限管理，不能使用 Windows 设备管理器中的顺序作为跨平台持久编号。
