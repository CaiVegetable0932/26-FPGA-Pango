# PRAW V1 千兆网视频协议与上位机核心实现

版本：实施细则 1.0 · 日期：2026-09-07
实现位置：host/src/pango_video · 运行目标：Python 3.12，Windows / Ubuntu 24.04
状态：已有可运行的主机接收核心和模拟验证；FPGA发送端、UART控制适配、真实千兆网与Ubuntu实机验证待完成。

## 1. 范围与兼容关系

本细则按[RAW8千兆网与HDMI双路回传方案](../../output/OV5640_RAW8千兆网与HDMI双路回传方案.md)§6实现，保留原有64字节应用头、版本1、小端字段、CRC32及1400字节载荷上限。该跨端方案仍是头布局权威来源；本文补齐分块、状态机、边界与主机API。后续修改应连同该方案、代码与固定向量一起评审，不能单方面改host或RTL。

连续视频为同一颗OV5640的S0 RAW8。S1及结果通过板端处理链与HDMI，不提供网络快照。PC不转发主视频，不实现实时几何矫正。本模块输出完整像素及来源元数据；当前GUI、采集与板端参数控制由独立模块提供，正式测评仍按证据验收。

推荐部署为FPGA到PC的独立有线IPv4单播链路，端到端IP MTU至少1500。50000（PC目的端口）、50001（FPGA源端口）仅是配置模板示例，不代表板端已分配或IANA登记。正式地址、端口、设备标识、源代次、尺寸及Bayer相位必须从板端配置和回读确认。

## 2. 一包的边界与字节序

~~~text
Ethernet头 | IPv4头(无选项20B) | UDP头(8B) | PRAW头(64B) | 图像块(1..1400B) | Ethernet FCS
                                              ↑ Python socket收到的区域 ↑
~~~

最大UDP载荷1464B、UDP长度1472B、IPv4总长度1492B，适配1500字节IP MTU。一个UDP数据报就是一块；不在UDP载荷中再扫描magic，不进行TCP式粘包处理。收到1465字节或更多应用数据直接拒绝，尾块后的额外字节也拒绝。

Ethernet/IP/UDP头由操作系统协议栈处理；其字段仍为标准网络字节序。只有PRAW应用头的多字节整数为小端，不允许直接映射有本机对齐填充的C结构体。接收用65535B复用缓冲，避免把超长数据报截成貌似合法的1464B。

UDP不自带可靠性、流控或拥塞控制。端到端MTU、发送节奏和网络容量必须验证；本V1不面向未知MTU的公网隧道。分片和突发的设计依据见[RFC 8085](https://datatracker.ietf.org/doc/html/rfc8085)。

### 2.1 64字节应用头对照

| 偏移 | 字段 | 类型 | V1解释 |
| --- | --- | --- | --- |
| 0 | magic | 4B | ASCII PRAW，即50 52 41 57 |
| 4 | protocol_version | u16 | 1；未知版本拒绝 |
| 6 | header_bytes | u16 | 64；V1不接受扩展头 |
| 8 | packet_type | u8 | 1 RAW_LIVE；2/3退役并拒绝 |
| 9 | flags | u8 | bit0重传；bit1最后分块；其他位必须0 |
| 10 | pixel_format | u16 | 1 RAW8；2 RGB888，RGB字节顺序 |
| 12 | stream_epoch | u64 | 源采集代次，不是网络连接会话 |
| 20 | frame_id | u64 | 同一代次内的真实输入帧身份 |
| 28 | param_version | u32 | 当前阶段的实际配置版本 |
| 32 / 34 | width / height | u16 / u16 | 默认1920 / 1080 |
| 36 | row_stride | u32 | 线上紧凑行跨度：RAW=width，RGB=3×width |
| 40 | frame_bytes | u32 | row_stride×height，不含DDR行填充 |
| 44 | payload_offset | u32 | packet_index×1400 |
| 48 | payload_bytes | u16 | 当前实际图像块长度 |
| 50 | bayer_code | u8 | RAW：1 RGGB、2 GRBG、3 GBRG、4 BGGR；RGB：0 |
| 51 | bit_depth | u8 | 8；RGB指每分量8位 |
| 52 / 54 | packet_index / packet_count | u16 / u16 | 索引从0开始，总数按图像长度计算 |
| 56 | packet_crc32 | u32 | 本字段视为4个零，校验64B头＋实际图像块 |
| 60 | descriptor_id | u32 | 当前源代次内的不可变描述符标识 |

stream_epoch/frame_id在其他语言中须用无符号64位整数处理，不可转成可能丢精度的浮点数。头中没有硬件时间戳、snapshot_id或全帧哈希；这些信息必须从对应描述符取得，不能用PC接收时间臆造。

### 2.2 固定分块的强制规则

设B为frame_bytes、C为1400，V1必须满足：

~~~text
packet_count  = (B + C - 1) // C
0 <= packet_index < packet_count
payload_offset = packet_index * C
payload_bytes  = min(C, B - payload_offset)
LAST_CHUNK     = (packet_index == packet_count - 1)
UDP实际载荷长度 = 64 + payload_bytes
~~~

只允许最后一块短于1400B。图像长度恰好整除1400时，尾块仍为1400B。块允许跨越图像行，不添加行头；网络发送前剔除DDR padding。RAW DDR stride2048对应网络1920；RGB DDR stride6144对应网络5760。

固定偏移和包数排除了重叠、空洞、可变分块及“包数齐但字节未覆盖”的歧义。每个合法索引接收一次即可证明全部有效字节覆盖，首块/尾块先到都能重组。LAST只说明索引位置，不说明该包最后到达；不能看到LAST就提交帧。

| 图像 | 紧凑长度 | 包数 | 最后偏移 / 最后长度 |
| --- | --- | --- | --- |
| 1920×1080 RAW8 | 2,073,600B | 1482 | 2,073,400 / 200B |
| 1920×1080 RGB888 | 6,220,800B | 4444 | 6,220,200 / 600B |

### 2.3 CRC与互操作向量

算法为CRC-32/ISO-HDLC：反射多项式0xEDB88320、初值0xFFFFFFFF、最终异或0xFFFFFFFF；标准检查串123456789结果0xCBF43926。线上CRC字段自身按小端保存。

CRC覆盖头部所有字段（CRC字段按零处理）和实际载荷，不覆盖Ethernet/IP/UDP标准头、不覆盖不存在的填充。重传时bit0改变，所以必须重新计算报文CRC。Python的zlib.crc32已包含初值/最终异或约定，不能额外再异或一次。

固定向量见[tests/vectors/praw_v1.json](../tests/vectors/praw_v1.json)。它是4×2 RAW8、载荷00..07的72字节数据报；CRC=0x0C934ED0，CRC字段字节为D0 4E 93 0C。向量用独立偏移写入和逐位CRC计算产生，测试另外检查主机编解码结果。它是合成向量，不是FPGA抓包；小尺寸必须显式使用测试格式策略。

CRC用于传输错误检测；peer过滤和CRC不提供设备密码学认证。主机存盘SHA-256用于档案一致性；没有板端全帧哈希时，board_frame_hash_verified始终false。

## 3. 数据格式与描述符规则

RAW_LIVE仅接受RAW8、合法Bayer和8位。已删除的类型2/3直接拒绝。尺寸、stride、总长度、索引、载荷长度、flags、CRC均先检查，再申请帧缓冲。默认接收策略锁定1920×1080；CLI还锁定配置中的Bayer相位。小图只能在显式mock或开发API参数中启用，不能作为1080p验收。

同帧不变字段包括：完整重组键、参数版本、格式、尺寸、stride、总长度、Bayer、位深和包数。仅索引、offset、块长度、flags及包CRC可因分块或重传而变化。

描述符按(device_id, stream_epoch, descriptor_id)定位，既有对象必须不可变。RAW描述符可以引用适用一段帧的固定采集配置；逐帧曝光/时间等仍需真实逐帧记录。参数更新应换版本/描述符，并在明确源帧边界生效。不能从“当前参数”回填历史帧。

所有样本默认measurement_ready=false；RAW元数据不构成板端S1/结果同源精度证据。

## 4. 帧身份、窗口与超时状态机

每个UDPReceiver只绑定一个确定设备和源IP/端口。设备之间不共享组帧器；内部完整键为：

~~~text
(stream_epoch, frame_id, packet_type, descriptor_id)
~~~

同一源帧同一类型如果出现不同descriptor_id，正在组装的RAW帧整体失败；不会生成两份“同帧”。仅组装RAW_LIVE。

~~~mermaid
stateDiagram-v2
    [*] --> Receiving: 合法RAW首包
    Receiving --> Receiving: 新索引 / 相同重复 / 乱序
    Receiving --> Complete: 所有合法索引覆盖
    Receiving --> Failed: 内容冲突 / 元数据冲突 / 超时 / 容量不足
    Complete --> Terminal: 输出不可变完整帧
    Failed --> Terminal: 记录失败与缺块
    Terminal --> Terminal: 迟到包丢弃并计数
~~~

| 项目 | 默认值 | 行为 |
| --- | --- | --- |
| RAW在途 | 4帧 | 第5帧到来时作废最早进入的在途RAW，记录capacity |
| RAW期限 | 首个合法包后100ms | 绝对期限，重复包不续期；缺包不补零 |
| RAW帧号窗口 | 64个源帧号 | 低于窗口的帧拒绝；终态记录随窗口有界清理 |
| 单图长度上限 | 8MiB | 收包前检查 |
| 重组像素缓冲 | 合计32MiB | 分配前检查总像素容量 |
| 预览队列 | 2帧，最多16MiB | 完整帧后丢旧显示任务，单独计数 |
| 归档队列 | 4帧，最多16MiB | 不覆盖已有待保存图；满时记录该帧拒绝 |
| 故障事件 | assembler 128条；receiver 256条历史 | 溢出单独计数，不能声称保存了完整故障逐条日志 |

收到不同内容的重复块时，仅在组帧期间做逐字节比较并整帧失败。帧完成或失败后已不再接收块，迟到包统一记为late_terminal，不能覆盖或再次提交旧帧；不把这种丢弃描述为“已证实重复内容相同”。

窗口只用于拒绝过老RAW及控制内存，不把frame_id当数组下标，不为跨度内的每个缺失帧分配对象。完全未见包的源帧不能通过“缺块超时”发现，因此另记live_unobserved_ids_in_span。它只覆盖已观察最小/最大源帧号之间，不知道测量窗口开始/结束外的漏帧，也不能区分FPGA主动丢弃和网络整帧丢失；正式验收需比对板端原子计数。

stream_epoch只接受控制层确认的采集代次。UDP包不能自动切换代次，避免旧包反向切回。PC重连建立新run_id，不要求正在运行的FPGA改epoch。真正采集重启调用set_live_epoch；它作废旧RAW。设备冷启动也须避免重用可能残留的(epoch, frame_id)；具体持久计数/唯一代次产生机制留给板端冻结，不能每次启动恒为0。frame_id不在同一epoch内回绕。

缓冲限制统计像素存储，另有位图、Python对象、事件和系统socket内存；完成时转不可变bytes会有一次整帧复制。预览和归档可能共享同一个bytes对象，消费者必须释放旧引用。队列有界不代表GUI可以无限持有帧，也不等于测得进程RSS。

## 5. 缺包与退役类型

RAW实时流不主动重传；期限内缺包整帧失败，完整源身份保持。PRAW类型2/3已删除，接收时在分配像素缓冲前拒绝；没有快照注册、重读、成对保存或释放API。RAW30网络预算仍为44,460包/s、像素62.208MB/s，预算不等于实测。

| 文件 | 已实现职责 |
| --- | --- |
| [protocol.py](../src/pango_video/protocol.py) | 固定头编解码、CRC、长度/格式/分块校验、参考分包器 |
| [reassembly.py](../src/pango_video/reassembly.py) | RAW窗口、乱序/重复/冲突、绝对期限、缺块段、完整帧/故障事件 |
| [receiver.py](../src/pango_video/receiver.py) | IPv4 UDP、来源端点过滤、复用接收缓冲、独立预览/归档有界队列 |

| [cli.py](../src/pango_video/cli.py) | 配置读取、后台归档线程、接收报告、显式本机模拟发送 |
| [praw.py](../scripts/praw.py) | 不依赖当前工作目录的启动入口 |

无socket的解码集成示例（项目已把host/src放入模块搜索路径时）：

~~~python
from pango_video.reassembly import FrameAssembler

assembler = FrameAssembler(device_id="由设备回读取得", stream_epoch=confirmed_epoch)
frame = assembler.feed(udp_datagram)  # 一个完整UDP载荷
if frame is not None:
    # frame.data是不可变的完整像素bytes，可交给有界队列
    assert len(frame.data) == frame.header.frame_bytes

assembler.expire()                   # 无包到来时也要定期执行
for event in assembler.drain_failures():
    record_failure(event)            # 上层持久化故障日志
~~~

feed/expire/set_live_epoch由一个接收所有者串行调用。GUI不能直接跨线程改组帧器，应通过控制消息交给所有者。UDPReceiver.run通过threading.Event请求停止，退出后再close。status读取在run退出后进行；实时状态页应向接收线程请求快照。

decode_datagram返回借用的只读memoryview，不拥有输入字节；下次复用接收缓冲前必须消费。feed会把新块复制到自有帧缓冲，CompleteFrame.data不受接收缓冲复用影响。

## 7. 原始证据与计数口径

CLI默认只接收/统计，archive_every=0；大于0时保存第一帧及之后每N个完整RAW帧中的一帧，选择点在网络完整计数之后。它不是全程录像。设N=1可以申请保存每帧，但磁盘或归档队列不足会明确失败，不能宣称无丢失记录。

~~~text
host/data/<run_id>/e<epoch>_f<id>_t<type>_d<descriptor>/
    image.raw 或 image.rgb
    metadata.json
host/reports/<run_id>/receiver.json
~~~

每个样本目录使用独占创建，已有目录不覆盖。先写像素.part并flush/fsync、重命名，再写metadata.json.part并提交。只将存在metadata.json且校验正确的目录看作完整单图。写入中断可能留下.part或无metadata目录，不应作为有效样本索引。Linux额外同步目录；断电持久性仍取决于文件系统与存储设备。

元数据记录源模式mock/replay/hardware_unverified、源帧键、尺寸、Bayer/RGB、stride、字节数、包数、主机SHA-256、接收单调时钟、描述符状态。没有UTC硬件时基转换时，不能用主机接收耗时报告FPGA处理延迟。

| 计数 | 解释 |
| --- | --- |
| datagrams_received / wrong_peer | socket接收数 / 源端点不匹配 |
| packets_rejected_* | CRC、长度、格式等拒绝原因 |
| packets_duplicate / out_of_order | 活动帧的相同重复 / 相对已见最大索引的乱序 |
| frames_failed_* / frames_rejected_memory | 超时、冲突、容量、停止、内存不足 |
| live_frames_complete / live_bytes_complete | 全覆盖且CRC通过的RAW，先于预览消费 |
| preview_frames_replaced | GUI/消费未及时取走的旧显示任务 |
| archive_frames_rejected / storage.error | 归档队列拒绝 / 实际磁盘写入失败 |
| live_unobserved_ids_in_span | 已观察帧号跨度内完全未出现的源帧数 |
| failure_history_overflow | 有界故障历史丢失条数；此时不能声称逐条故障证据完整 |

无GUI的CLI会出现preview_frames_replaced，这是预览任务未消费；不能据此改写网络完整帧数。接收报告的fps使用整个接收窗口，包含等待发包的空闲时间。mock发送器的requested_fps是设定值，实际用elapsed_seconds与计数判断；短回环不能代替长稳或千兆网验收。

普通HDMI身份始终另管。这里不会用RAW帧号填充HDMI的source_frame_id；归档中hdmi_source_frame_id=null、hdmi_pairing_status=unverified。S0软件预览不等于FPGA S1，连续HDMI同源配对仍须独立证明。
