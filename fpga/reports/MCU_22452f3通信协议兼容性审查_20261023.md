# 当前 FPGA 与 MCU 22452f3 通信协议兼容性审查

日期：2026-10-23。范围仅为 FPGA↔F4 独立只读通信协议，以及收到的 MCU 状态能否作为当前 FPGA 姿态输入。不将 PC→F4 运动控制或 F4→F1 内部协议当作 FPGA 协议。

## 结论

**线格式和正常会话兼容；事件重连语义存在已复现的不兼容，姿态新鲜度策略尚未对齐。当前整板设计尚不能直接接线使用 MCU 姿态。**

通过真实提交的 MCU C 打包/请求处理代码与 FPGA RTL 验证，GET_INFO、OPEN_SESSION、GET_CONFIG、SET_STREAM、SYNC、STATE、首次 EVENT/ACK 的正常路径可互通。不能因此将重连恢复、姿态有效性、配置批准或物理链路判为全部兼容。后续板级更新已接通独立UART、会话与配置批准消费者的软件路径；本报告最初记录的顶层禁用状态是历史快照，不再代表当前RTL，详见发现4及[板级执行记录](MCU板级接入执行记录_20261023.md)。

## 发现与影响

### 1. P2：新会话事件起点与 GET_INFO 事件起点不一致，重连会停止确认事件

MCU `f4_link.c:310` 的 GET_INFO 返回基于**旧会话 ack**的首个未确认事件；`:324` 的 OPEN 新会话却把 ack 重置为 `oldest_event-1`，随后 `:694` 从这个位置重放。

FPGA `mcu_readonly_client.sv:243` 用 GET_INFO 初始化 `ack_target/last_event`；`:247` 收到 OPEN 成功后没有重新同步事件起点；`:228` 仅接收 `event_id==ack_target+1`，小于等于当前水位的事件不再确认。

已复现序列：

1. MCU 日志保留事件 1～7，旧会话已确认到 5。
2. FPGA 查询 INFO，得到首个未确认事件 6，将本地 ack_target 设为 5。
3. FPGA 打开新会话，MCU 把 ack 重置为 0，发送事件 1。
4. FPGA 丢弃事件 1，不发送 ACK；MCU 继续重发事件 1，事件 6 永远到不了 FPGA。

这是事件子通道停滞，STATE/SYNC 不一定停止。若持续产生事件，可能进一步触发 MCU 事件日志溢出。事件日志因溢出跳过期望 ID 的恢复也未在当前 FPGA 中闭合。

建议统一“新会话事件基线”语义：新会话建立后重新获取该会话的事件起点并完成初始化，或在 OPEN 响应中明确提供起点；同时约定日志缺口及旧事件重放的处理。不能直接确认尚未实际接收的事件来绕过问题。

### 2. P2：MCU 将反馈有效窗口从 20ms 改为 250ms，FPGA 姿态选择仍只允许 20ms

指定提交 `pose_config.h:21` 为 `POSE_STALE_US=250000`；`f4_link.c:234`～`:243` 可将年龄小于等于此门限的舵机反馈标为角度有效。GET_CONFIG body +80 也返回 250000。

FPGA `pose_frame_selector.sv:8` 固定 `MAX_AGE_US=20000`，`:95` 判断映射后的采样年龄加误差是否超过 20ms。它不从 GET_CONFIG 自动采用 250ms。

已验证：MCU 实际 builder 生成的 100ms 旧反馈仍带双角有效位；在测试显式合成标定批准后，FPGA 在年龄 101000us 时返回 `status=3`，无法用于当前帧姿态补偿。

这是运行语义和可用性差异，不是长度或字段错位。200Hz STATE 发送不等于舵机反馈每 5ms 更新。FPGA 拒绝旧测量具有合理保护作用，**不应为兼容直接将几何输入门限放宽到 250ms**；应分别约定控制存活窗口与视频补偿新鲜度，并测量反馈时间和映射误差。

### 3. 现有标定保护：默认固件状态可解析，但不能作为已标定姿态

MCU `pose_config.h:24` 保持 `POSE_CONFIG_VERIFIED=0`，因此 STATE flags bit7 为 0（`f4_link.c:223`）。FPGA `pose_frame_selector.sv:96`～`:97` 要求该位有效，否则返回 `status=4`。

本次真实默认 STATE 测试得到 status=4；仅在明确标为合成的测试分支设置 bit7 后，新鲜的编码器姿态得到 status=0。该保护与项目现有约定一致，不是本次新引入的协议错误。GET_CONFIG 的外部 `config_approved` 与 STATE bit7 是两个独立条件；只批准前者不会自动批准后者。

### 4. 历史板级入口缺口：软件接入已完成，物理验收仍未完成

最初审查快照的 `pango_video_system.sv:251`～`:255` 将 `mcu_enable/rx_valid/tx_ready/timing_valid/config_approved/config_ready/new_session/event_ready` 等保持禁用或常量。当时内部MCU字节协议客户端虽已接入，整板顶层不能实际发起测试会话；上述旧行号及结论仅用于解释原始证据。

本轮后续实现已提供独立UART字节收发、会话控制、完整配置校验与kind12策略批准消费者，并接入事件消费及姿态门禁。当前板端使用完整264字节配置的CRC32/boot/version绑定批准，资源优化不等于跳过配置校验；客户端默认完整实体模式仍供兼容使用。链路启用和批准由策略控制，不因软件接通而绕过复位、会话、标定或新鲜度保护。当前实现和冻结源码/回归哈希见[板级执行记录](MCU板级接入执行记录_20261023.md)。

MCU FPGA口仍是 `links[1]` / USART6，460800、8N1；PC口的查询超时、流率和权限不同，不能混接或混用。引脚方案和RTL接通不是物理验收：真实接线、电平、UART时钟误差、传感器时间映射和标定边界仍待验证。发现1的事件重连问题、发现2的250ms/20ms策略差异以及发现3的默认配置未验证保护仍然存在。

本项原本属于板级集成缺口，不作为字节协议格式不兼容。其软件部分已由后续实现补齐；本报告不批准下载或硬件运行，也不把软件回归写成实板链路通过。

## 实际验证与复现

证据目录：`mcu/build/protocol-review-22452f3/`。

运行 `python -B mcu/scripts/review_fpga_protocol_22452f3.py`：

- 用 GCC 编译未修改的目标提交 f4_link.c/wire.c；只有硬件边界使用测试 stub。
- 经真实 MCU parser/handler 生成 INFO/OPEN/CONFIG/STREAM，生成 SYNC、STATE 和由真实发布逻辑选择的事件报文。
- Icarus 运行当前 mcu_readonly_client + uart_v2_parser + pose_frame_selector；正常握手、编码器字段、首次事件确认通过。
- 独立 Python codec 核对 FPGA 实际发出的11个请求帧，包括CRC、长度、上下文和命令载荷，全部逐字节一致。
- 复现事件重连停滞；验证未批准姿态拒绝、合成批准的新鲜姿态接受、MCU仍有效的100ms旧姿态被FPGA拒绝。
- 测试源码SHA-256在运行前后保持一致。详细结果为 `result.json`，输出为 `rtl.log`；编译日志保留上游未使用诊断函数的告警。

测试在受控场景中提供 `new_session=100`、`config_ready/config_approved=1` 和合成时间边界；这些不是正式顶层已具备能力的证明。未运行完整固件硬件仿真、PDS综合或真实UART联调。

为核对仿真边界，只读查阅安装版 PDS 2022.2-SP6.4 `Simulation_User_Guide.pdf` 的 top/仿真设置章节，并对照 `reference/盘古100K200K MINI开发板/1_Demo_document/实验例程说明篇/教程1_盘古MINI系列开发板硬件指导手册_V1.3.pdf` 第6页的PG2L100H/-6/FBG676目标。官方目录无写入。本次为不依赖器件IP的字节级RTL验证，不替代PDS或目标板验收。
